## 1. System Overview

Report Center is a generic, configurable report viewer system. A single `ReportViewerClient` component renders 20+ inventory reports through declarative profile configs. All SQL executes through a central MSSQL gateway with mandatory read-only validation.

```
Browser → Next.js GET /api/reports/inventory → SQL Gateway → MSSQL → Response
                ↑                                              ↓
         ReportViewerClient ← JSON Payload ←─────────────────┘
```

**Key facts:**
- **1 API route** (`inventory/route.ts`, ~3,520 lines) handles **all inventory reports**
- **20 async handler functions** dispatched via `reportHandlers` object
- **2 data sources**: `db_ptrj` (estate) and `db_ptrj_mill` (pabrik)
- **Client-side filtering** via `applyReportFilters()` — operates on `DbRow[]` returned from MSSQL
- **Read-only enforcement** at the route layer via `validateReadOnlySql()` before any gateway call

## 3. Data Flow: Full Request Lifecycle

```
1. User opens /report-center/inventory/stok-gudang
2. ReportViewerClient reads InventoryReport profile from inventory/config.ts
3. Client renders: title, description, KPI cards, chart selector, filter bar
4. User applies filters → fetchReport() builds URLSearchParams
5. GET /api/reports/inventory?report=stok-gudang&source=estate&limit=500&...
6. GET handler:
   a. getSource(request) → 'estate' | 'pabrik'
   b. sourceToContext(source) → QueryContext {server, database}
   c. getInventoryReport(reportParam) → InventoryReport profile
   d. reportHandlers[apiReport] → stockSummary handler function
   e. handler({limit, search, ctx, stale, filters}) executes:
      - Builds SQL template literal
      - Calls querySQL(ctx, sql):
        • validateReadOnlySql(sql) → BLOCKS if non-read
        • POST ${BASE_URL}/v1/query {sql, server, database}
        • Returns GatewayResult {success, data: {recordset}}
      - Wraps result in ReportPayload
   f. Returns NextResponse.json(payload)
7. Client receives: {title, rows, columns, summary, chart, metadata}
8. Client applies applyReportFilters() client-side on rows
9. Client renders table (grouped), KPI cards, chart via viewerProfile
```

```typescript
// inventory/route.ts:37-42
function databaseForServer(server: string) {
  if (process.env.DATABASE_NAME) return process.env.DATABASE_NAME  // env override
  if (server === 'SERVER_PROFILE_2') return 'db_ptrj'              // estate
  if (server === 'SERVER_PROFILE_3') return 'db_ptrj_mill'        // pabrik
  return 'db_ptrj'
}

// inventory/route.ts:56-59
function getSource(request: NextRequest): ReportSource {
  const raw = (request.nextUrl.searchParams.get('source') ?? '').trim().toLowerCase()
  return raw === 'pabrik' || raw === 'mill' || raw === 'factory' ? 'pabrik' : 'estate'
}
```

### 4.3 SQL Gateway

```typescript
const BASE_URL = process.env.SQL_GATEWAY_URL
```

`SQL_GATEWAY_URL` and `SQL_GATEWAY_API_KEY` are server-side configuration only. Do not hard-code fallback credentials, do not expose gateway tokens to client components, and return a sanitized configuration error when either value is missing.

### 8.4 `applyReportFilters()` — 7-Step Pipeline

```
Input: FilterablePayload {rows, columns, summary, chart?, metadata?}
       + ReportFilterInput {search, period, columnFilters, ...}

Step 1  inferReportSchema(payload)
         → scans rows[0..24], infers type per column, assigns operators

Step 2  sanitizeFiltersForSchema(...)
         → validates columnFilters against schema, normalizes field names

Step 3  activeFiltersToRecord(filters)
         NO active → return payload with empty appliedFilters
         YES active → proceed

Step 4  filter: rows.filter(row → rowPassesFilters(row, filters))
         Evaluates ALL of:
           • text search (contains)
           • location, category, supplier, status, vehicle
           • MovementCategory equality
           • date filters (period YYYY-MM, dateFrom, dateTo)
           • blankField (null/''/'-')
           • columnFilters (per ReportColumnOperator)
           • minQty, minAmount

Step 5  sort: sortRows() by metricValue or explicit sortColumn

Step 6  window: rowStart-1, rowEnd, top?, resultLimit

Step 7  output:
           rows       = filtered + paginated
           columns    = Object.keys(rows[0])
           summary    = createFilteredSummary(matchedRows, totals, filters)
           chart      = createFilteredChart(matchedRows, filters, fallback)
           metadata   = { reportSchema, appliedFilters, filteredRows, ... }
```

### 8.5 Read-Only Validation (`validateReadOnlySql`)

**Location:** Runs inside `querySQL()` — **before** the gateway call. No SQL reaches the gateway without passing this.

**Preprocessing:**
1. Replace string literals `'...'` → `''`
2. Strip `--` single-line comments
3. Strip `/* ... */` block comments
4. Collapse whitespace

**Validation (in order):**

```typescript
// 1. Must start with SELECT or WITH
if (!/^(select|with)\b/i.test(normalized))
  return { safe: false, reason: "Query harus diawali SELECT atau WITH." }

// 2. Blocked keyword regex
if (/\b(insert|update|delete|drop|alter|truncate|merge|exec|execute|
       create|grant|revoke|deny|backup|restore|dbcc|use|kill|waitfor|
       openrowset|openquery|bulk|xp_[a-z0-9_]+|sp_[a-z0-9_]+)\b/i.test(normalized))
  return { safe: false, reason: "Operasi non-read diblokir.", blockedTerms: [...] }

// 3. SELECT ... INTO
if (/select\b[\s\S]*\binto\b/i.test(normalized))
  return { safe: false, reason: "SELECT INTO diblokir karena membuat objek baru." }
```

**NL Filter Safety:** Natural language queries (`naturalQuery` param) are **never executed as SQL**. They go through `parseNaturalFilterLocally()` → `ReportFilterInput` → `applyReportFilters()` (client-side only).

### 9.1 Classification Rules

```typescript
// From StockIssueEventCount (event count over period) + quantityClosing (current stock)
function movementCategoryFromIssueCount(issueCount: unknown, quantityClosing: unknown): MovementCategory {
  if (issueCount >= 6)                    return 'Fast Moving'     // ≥6 events
  if (issueCount >= 2)                   return 'Moving'          // 2-5 events
  if (issueCount === 1)                   return 'Slow Moving'     // 1 event
  if (quantityClosing > 0)                 return 'Dead Stock'       // stock exists, no movement
  return 'Stale'                                                   // zero stock, zero movement
}
```

### 9.3 SQL CASE Expressions

**Basic:**
```sql
CASE
  WHEN StockIssueEventCount >= 6                          THEN 'Fast Moving'
  WHEN StockIssueEventCount BETWEEN 2 AND 5               THEN 'Moving'
  WHEN StockIssueEventCount = 1                           THEN 'Slow Moving'
  WHEN quantityClosing > 0                                 THEN 'Dead Stock'
  ELSE 'Stale'
```

## 17. Interactive Inventory Rollout Rules

### 17.1 Global Module Registry

The first-level Report Center modules are owned by `REPORT_GLOBAL_MODULES`:

- Procurement
- Payroll
- Human Resources
- Financial
- Budget

Payroll and Human Resources remain separate top-level modules. Legacy aliases may route to these modules, but RBAC must use the existing registry permission keys and must not grant broader access implicitly.

### 17.2 Taxonomy vs Movement

Inventory reports must keep stored item taxonomy separate from computed movement semantics:

- `Item Code`, `Item Type`, `Product Type`, `Product Category`, `StockAnalysisCode`, and `Location` are stored or source taxonomy dimensions.
- `MovementCategory` is computed for the selected actual/accounting period.
- `StockAnalysisCode` and `MovementCategory` can be compared in the UI, but must not normalize into one field or reuse the same filter key.

### 17.3 KPI And Detail Scope

Inventory KPI and breakdown values are full-scope analytics for the normalized filter scope. They must not be recomputed from visible tiles, current page rows, virtualized table windows, or bounded detail responses.

Detail windows must declare total rows, filtered rows, returned rows, partial state, page/window/balanced strategy, and reason. Pagination or row limit changes may change table rows, but must not change server KPI totals for the same normalized filters.

### 17.4 AI Server Configuration

AI features are server-side only and read these environment variables:

- `ANTHROPIC_AUTH_TOKEN`
- `ANTHROPIC_BASE_URL`
- `ANTHROPIC_MODEL`
- `API_TIMEOUT_MS`

Provider calls use the Anthropic Messages-compatible endpoint. Timeout is bounded by the provider helper; extremely large timeout values must be clamped. Client components and API responses must never include credentials, raw provider request bodies, authorization headers, gateway keys, or raw SQL.

When AI is unavailable, report controls must remain usable and the UI must show deterministic local insight based on sanitized payload evidence.

### 17.5 Rollout Gate

Only the Procurement Inventory vertical slice is approved for the interactive analytics experience while validation is in progress. Other global modules remain catalog/navigation experiences until they have:

- a typed analytics contract,
- semantic dimensions,
- full-scope KPI/breakdown source,
- filter-action mapping,
- bounded AI evidence,
- responsive visual QA,
- security scan with no secret leakage,
- TypeScript, targeted tests, scoped lint, build, live smoke, and documented fallback behavior.
